# Qualify the governed Software Factory end to end

## Problem Statement

Mission Control has durable subsystem proofs for Missions, planning, worker execution, verification, publication, exact-current acceptance, observability, Remote Sandbox, Factory Memory, Progressive Factory UX, and Factory Learning. It does not yet have one bounded qualification that proves those canonical implementations compose into a single governed system with exact lineage, explicit authority boundaries, deliberate failures, recovery, browser evidence, and a durable final decision.

## Findings

- Exact `origin/main` baseline is `3de80b97c7272f64586e5d08bc7c73fcd2114faa`.
- Runtime contract is v26 in `convex/lib/runtimeContract.ts`.
- PR #109 Remote Sandbox (`e32444a2aecb67bfcb050cd4a92d11d8de650db8`) and PR #110 Factory Learning (`3de80b97c7272f64586e5d08bc7c73fcd2114faa`) are both reachable from the baseline.
- Existing proofs cover the constituent systems, but no top-level `qualify:factory` command currently composes the required lineage and failure-injection matrix.
- The qualification must add no product scope and may fix production code only when a machine-checkable invariant exposes a real blocker.

## Proposed Solutions

### Option 1: Documentation-only aggregation

**Approach:** Reference existing test suites and prior evidence without creating a composed qualification.

**Pros:** Minimal change and fast execution.

**Cons:** Does not satisfy deliberate failure injection, exact cross-system lineage, or evidence generated by this qualification.

**Effort:** Low

**Risk:** High because it can produce a false system-level confidence claim.

### Option 2: Thin composed qualification over canonical implementations

**Approach:** Add one deterministic fixture and top-level qualification command that reuses existing domain functions, Convex test infrastructure, worker tests, FakeSandboxProvider, browser E2E, and validation commands. Persist redacted machine-readable evidence and a human-readable decision packet.

**Pros:** Proves composition without duplicating architecture or adding product behavior; fails non-zero on exact invariant violations.

**Cons:** Requires careful fixture design and a longer validation cycle.

**Effort:** High

**Risk:** Medium, contained to tests, fixtures, scripts, and documentation unless a blocker is proven.

## Recommended Action

Use Option 2. Build the smallest composed qualification around existing canonical code and tests, exercise the required failure and recovery cases, validate the real UI at 1440/1024/390 in light and dark modes, and publish only if the full matrix passes. Do not run live exe.dev, reopen PR #89, or introduce any public runtime contract change.
